# Poem — Руководство пользователя сервера (`guide_server.md`)

Поэма (Poem) — civ-like игра, в которой игрок управляет цивилизацией через текстовые законы, а симуляция мира выполняется на сервере с использованием нейросетевых слоёв (валидация текстов законов, генерация изображений хроники). **Все нейросетевые вычисления, включая генерацию изображений, выполняются на собственных видеокартах сервера; сторонние облачные сервисы и внешние API не используются.**

Данное руководство описывает установку и запуск **серверной части** (`poem_sim`). Клиентская часть описана в `guide_client.md`, правила игры — в `rules.md`.

---

## 1. Состав сервера

Серверная часть находится в каталоге `poem_sim/`:

```text
poem_sim/
├── pyproject.toml          # пакет poem-sim 0.4.0, Python >= 3.11
├── pytest.ini              # конфигурация тестов
├── schema.sql              # схема БД PostgreSQL для продактив-развёртывания (§14)
├── config/
│   └── chronology.toml     # таблица интервалов ходов по эпохам, скорости игры (§8)
├── poem/                   # доменное ядро (все состояния — серверные)
│   ├── core.py             # доменные типы: Law, LawDraft, LawRevision, SimDuration, Turn…
│   ├── chronology.py       # хроника мира, эпохи, динамические интервалы ходов (§6–§10)
│   ├── laws.py             # LawStore: черновики, ревизии, история версий (§3)
│   ├── pricing.py          # стоимость правок законов (только игровые факторы, §5)
│   ├── turn.py             # движок хода: срез, снапшот законов, симуляция (§4, §12–§13)
│   ├── views.py            # проекции отчёта хода для клиента + очередь задач генерации картинок (§13.19–20, §16)
│   ├── chronicle_report.py # литературный отчёт правителя: стихи/эпосы/плачи о ходе (§13.22)
│   ├── llm.py              # опциональная LLM-генерация игровых текстов (выключена по умолчанию)
│   ├── api.py              # HTTP-обработчики /api/v1/… (WorldServer.handle, §15)
│   └── config.py           # загрузка и валидация chronology.toml (TASK-065)
└── tests/                  # 172 автотеста, проверяющих правила Rev 3
```

Важные свойства архитектуры (см. `design.md`, §20):

- все правки законов (черновики и ревизии) хранятся **только на сервере**;
- симуляция хода читает детерминированный серверный снимок активных законов;
- реальное время суток не влияет на стоимость и эффективность правок — только логический срез `simulation_cutoff`;
- каждый ход продвигает игровое время на переменный интервал (Civilization-like), договоры/переходы/путешествия живут в игровом времени.

## 2. Требования к аппаратному обеспечению

### 2.1. Минимальные (разработка, тесты, одиночный мир «для себя»)

| Компонент | Требование |
|---|---|
| CPU | 2 ядра / 4 потока, x86-64 или ARM64, от 2 ГГц |
| RAM | 4 ГБ — **без генерации изображений** (in-memory состояние одного мира); 8 ГБ — если на этой же машине запускается воркер генерации (модель целиком размещается в памяти видеокарты, но плюс ~2–4 ГБ системной RAM на процесс воркера и конвейер) |
| Накопитель | 10 ГБ свободно (код, БД, кэш изображений) + ~15 ГБ на локальные модели генерации (веса диффузионных моделей SDXL/Flux) |
| GPU | **не требуется**: сервер может работать вообще без генерации картинок (задачи остаются в очереди `queued`, отчёт доступен без иллюстраций) |
| Сеть | доступ в интернет нужен только для первоначальной загрузки весов моделей; сама генерация выполняется полностью локально, без обращений к сторонним сервисам |

### 2.2. Рекомендуемые (эксплуатация, несколько миров)

| Компонент | Требование |
|---|---|
| CPU | 4–8 ядер (симуляция хода однопоточна, но миры и задачи генерации параллельны) |
| RAM | 16–32 ГБ (состояние миров + процессы воркеров генерации) |
| Накопитель | 50+ ГБ NVMe SSD (БД PostgreSQL + веса локальных моделей + растущая коллекция изображений хроники) |
| GPU | **требуется для генерации изображений хроники (нейросетевой слой §13.20)** — сервер рендерит иллюстрации **на собственных видеокартах**, без использования сторонних облачных сервисов и API. Ядро симуляции `poem` GPU не использует; видеокарта нужна только процессу воркера-рендерера. Ориентиры: NVIDIA 12+ ГБ VRAM (RTX 3060 12GB / RTX 4060 Ti 16GB) для SDXL при 1024×1024; 16–24 ГБ (RTX 4080/4090, A100) для Flux и нескольких одновременных задач. На одну видеокарту можно запустить несколько воркеров-процессов — очередь задач (`claim`) рассчитана на конкурентный поллинг |

Ориентир масштабирования: состояние одного мира (законы, ревизии, фольклор, события) полностью находится в памяти между ходами; тяжёлые расчёты выполняются в момент `run_turn`, поэтому пиковая нагрузка привязана к числу одновременно финализируемых ходов.

## 3. Требования к программному обеспечению

| ПО | Версия | Назначение |
|---|---|---|
| Python | **>= 3.11** (проверено на 3.12) | язык ядра; используется `tomllib` из стандартной библиотеки (доступен только с 3.11) |
| pip / venv | любой актуальный | установка пакета `poem-sim` |
| setuptools | >= 68 | сборка пакета (build-system в `pyproject.toml`) |
| pytest | >= 7 (опция `[test]`) | прогон тестов |
| PostgreSQL | 14+ | **только для продактив-развёртывания**: схема `schema.sql` использует типы `UUID` и `JSONB`. Встроенное ядро работает на in-memory хранилище (`LawStore`) и внешнюю БД не требует |
| ОС | Linux (рекомендуется), macOS, Windows | сервер переносим, сторонних системных зависимостей нет |
| Драйвер GPU | NVIDIA Driver, совместимый с CUDA 12.x (для воркера генерации; для AMD — ROCm) | нужен **только** процессу воркера-рендерера изображений |
| Фреймворк инференса | PyTorch с CUDA-сборкой + локальная диффузионная модель (SDXL / Flux через diffusers, либо ComfyUI) | автономная генерация иллюстраций хроники на видеокартах сервера; установка не требуется, если генерация отключена |

Зависимости Python-пакета (`pyproject.toml` → `dependencies = []`): у ядра `poem` **нет внешних зависимостей runtime**. Единственная обязательная зависимость — сам Python ≥ 3.11. Стек генерации изображений (PyTorch, diffusers и т.п.) устанавливается **отдельно**, только в окружение воркера-рендерера: ядро симуляции с ним не связанно и работает без него.

**Принципиальная архитектурная особенность:** все нейросетевые вычисления сервера — генерация изображений хроники (§13.20) и семантическая валидация текстов законов — выполняются **на собственных вычислительных ресурсах сервера (его видеокартах)**. Сервер не отправляет данные игры, промпты или тексты законов во внешние облачные сервисы и сторонние API генерации; после первоначальной загрузки весов моделей работа возможна полностью в изолированной сети (air-gapped).

HTTP-слой (`poem/api.py`) написан фреймворк-независимо: обработчики принимают/возвращают обычные JSON-совместимые словари и могут быть подключены к FastAPI, aiohttp или Flask без изменения доменной логики. Для продактива дополнительно понадобятся выбранный веб-фреймворк и драйвер PostgreSQL (psycopg).

## 4. Порядок установки

### 4.0. Автоматизированный чек-лист требований и развёртывание (`deploy.sh` / `deploy.bat`)

В корне репозитория лежат скрипты развёртывания сервера: **`deploy.sh`** (Linux/macOS) и **`deploy.bat`** (Windows). Оба сначала проверяют чек-лист аппаратных (§2) и программных (§3) требований, затем выполняют развёртывание (venv + `pip install -e ".[test]"` + проверка импорта пакета и загрузки `config/chronology.toml`).

```bash
# Linux
./deploy.sh check                       # только чек-лист (профиль min — по умолчанию)
./deploy.sh check --profile=prod        # строгий чек-лист продактива (CPU/RAM/диск/PostgreSQL/GPU)
./deploy.sh deploy                      # чек-лист + развёртывание (прерывается при FAIL)
./deploy.sh test                        # прогон pytest в развёрнутом .venv
```

```bat
rem Windows (cmd.exe)
deploy.bat check
deploy.bat check /profile:prod
deploy.bat deploy
deploy.bat test
```

Пункты чек-листа помечаются `[PASS]` / `[WARN]` (опциональный слой не выполнен — GPU, PostgreSQL для не-prod) / `[FAIL]` (обязательное требование нарушено; скрипт возвращает код 1 и прерывает развёртывание, если не задан `--force` / `/force`). Пороги профилей соответствуют таблицам §2.1–2.2: `min` — 2 ядра / 4 ГБ RAM / 10 ГБ диска; `recommended` и `prod` — 4 ядра / 16 ГБ RAM / 50 ГБ диска; `prod` дополнительно требует PostgreSQL 14+ (`schema.sql` использует `UUID`/`JSONB`, п. 4.3). Опции: `--dir` / `/dir` (каталог `poem_sim`), `--python` / `/python` (интерпретатор), `--skip-gpu` / `/skip-gpu`.

### 4.4. Конфигурация

Файл `config/chronology.toml` (§8) редактируется без изменения кода:

- `speed` — `quick` / `standard` / `epic` / `marathon` (множители 0.67 / 1.0 / 1.5 / 3.0);
- `era_source` — как определяется эпоха мира: `leading_civilization`, `median_active_civilizations` (по умолчанию, рекомендовано для конкурентной игры), `weighted_average`;
- `[[chronology.intervals]]` — годы на ход для каждой эпохи (заря 60, древняя 40, классическая 25, средневековье 20, Возрождение 10, индустриальная 5, современная 2, атомная 1, информационная 0.5, планетарная 0.25);
- `[chronology.calendar]` — длина года и число сезонов (мир может быть и на чужой планете).

Конфигурация валидируется при загрузке (`poem/config.py`): ошибка будет, если не задан интервал для какой-либо эпохи или указана неизвестная скорость/источник эпохи.

Дополнительно тексты литературного отчёта правителя (§13.22) могут генерироваться LLM (`poem/llm.py`). **По умолчанию режим выключен** — используются детерминированные шаблоны хроники; сетевые вызовы не совершаются. Включение — переменными окружения процесса сервера:

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `POEM_LLM_ENABLED` | выкл. | `1` включает LLM-генерацию текстов отчёта |
| `POEM_LLM_PROVIDER` | `openai` | `openai`/`http` (OpenAI-совместимый `/chat/completions`), `command` (локальный CLI-мост через stdin/stdout) |
| `POEM_LLM_MODEL` | — | имя модели |
| `POEM_LLM_API_KEY` / `POEM_LLM_API_KEY_FILE` | — | ключ доступа (или путь к файлу с ключом, например `/run/secrets/…`) |
| `POEM_LLM_BASE_URL` | `https://api.openai.com/v1` | базовый URL (для локального Ollama/llama.cpp — напр. `http://localhost:11434/v1`) |
| `POEM_LLM_COMMAND` | — | argv CLI-моста при `provider=command` |
| `POEM_LLM_TIMEOUT` | `20` | таймаут запроса, секунд |
| `POEM_LLM_STYLE` | — | дополнительный стилистический указ в системном промпте |

Гарантии: промпты строятся только из устойчивых игровых данных (id, названия, игровые годы) — без wall-clock времени; ответы кэшируются по хешу промпта (повторный ход с теми же фактами даёт побайтово тот же отчёт); при любом сбое провайдера, таймауте или неприемлемом ответе секция отдаётся шаблонным текстом — публикация хода не может «сломаться» из-за LLM. Токены стороннего API — только серверные; клиент (тонкий, ui-client.md) ничего о генераторе не знает.

### 4.4a. Аутентификация администратора сервера (§15 security addendum)

Все изменяющие HTTP-маршруты (`POST`/`PUT`/`DELETE`/`PATCH`: законы, черновики, ревизии, ходы, войны, договоры, регистрация цивилизаций) требуют учётных данных администратора. Только чтение (`GET`) остаётся публичным — тонкий клиент опрашивает состояние мира без токена.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `POEM_ADMIN_TOKEN` | пусто (сервер открыт — только для тестов/локальной игры) | административный токен сервера |
| `POEM_IMAGE_WORKER_TOKEN` | пусто | отдельный токен GPU-воркера рендера иллюстраций |

Токен выдаётся командой (криптостойкий, 256 бит):

```python
from poem.api import generate_admin_token
print(generate_admin_token())   # → например, "kQ3…url-safe"
```

Способы передачи учётных данных в запросе (первый найденный выигрывает):

- заголовок `Authorization: Bearer <token>`;
- заголовок `X-Auth-Token: <token>` (или `X-Admin-Token`);
- поле `auth_token` / `admin_token` в JSON-теле — для фреймворков, проксирующих только method/path/body;
- для эндпоинтов рендера изображений дополнительно принимается `X-Worker-Token` / поле `worker_token` — воркер имеет право только на свои маршруты, полный доступ даёт админский токен.

Поведение: сравнение токенов выполняется за постоянное время (`hmac.compare_digest`), поэтому ни длина, ни префикс неверного токена не утекают через время ответа. Ответы: `401` — учётные данные не предоставлены (с подсказкой, как их передать), `403` — предоставлены неверные. Если `POEM_ADMIN_TOKEN` не задан, проверка пропускается (режим разработки); в продактив-развёртывании токен обязателен. Реализация — `poem/api.py` (`_check_admin`, `_check_worker_or_admin`, `handle`), тесты — `tests/test_admin_auth.py`.

### 4.5. Установка воркера генерации изображений (локальные GPU)

Генерация иллюстраций хроники — опциональный нейросетевой слой (§13.20). Он выполняется **на видеокартах самого сервера**, сторонние сервисы не используются. Ядро `poem` при этом остаётся без зависимостей: стек инференса ставится в **отдельное** виртуальное окружение воркера.

```bash
# отдельное окружение рендерера (не смешивать с ядром)
python3.11 -m venv ~/poem-renderer-venv
source ~/poem-renderer-venv/bin/activate

pip install torch torchvision --index-url https://download.pytorch.org/whl/cu121  # CUDA-сборка
pip install diffusers transformers accelerate safetensors pillow

# скачивание весов модели ОДИНАЖДЫ (после этого генерация работает офлайн)
hf download stabilityai/stable-diffusion-xl-base-1.0 \
    --local-dir ~/models/sdxl
# либо другая локальная модель (Flux и т.п.) на усмотрение оператора
```

Воркер-скрипт (`renderer.py`) типично выглядит так: поллинг очереди задач мира → `POST /images/{id}/claim` (с `worker_id` и сроком аренды `lease_seconds`) → локальный инференс на GPU → `POST /images/{id}/complete` с готовыми байтами в `asset_base64` (сервер сам сохранит файл в своём каталоге `asset_dir`, путь задаётся относительным `asset_ref` либо генерируется из id задачи) — либо, при расшаренном томе, сохранение PNG напрямую и `complete` только с `asset_ref`. Для долгих рендеров воркер периодически вызывает `POST /images/{id}/heartbeat`, продлевая аренду. Если воркер упал (OOM, перезагрузка машины) и аренду не продлил, сервер по истечении `lease_expires_at` автоматически возвращает задачу в `queued` — другой воркер подхватит её, изображение не теряется. Промпт задачи воркер получает из самой задачи (он формируется ядром детерминированно из данных отчёта хода — см. `queue_image_tasks`, §13 шаг 20), поэтому результат воспроизводим.

Мониторинг конвейера для админ-панели: `GET /api/v1/worlds/{id}/images/metrics` возвращает глубину очереди по статусам, загрузку каждого GPU-воркера (`by_worker`), число возвратов осиротевших аренд, среднее время ожидания и рендера, долю успешных задач. Опрос метрик не меняет состояние очереди — панель может опрашивать её часто.

Готовые иллюстрации клиент получает **с самого сервера**: `GET /api/v1/images/{task_id}/asset` возвращает байты файла из собственного хранилища сервера (base64 + media_type + sha256); внешних CDN/объектных хранилищ в цепочке нет (§20.4). Пути `asset_ref` песочницаются: абсолютные пути и «..» отклоняются, запись возможна только внутри `asset_dir`.

Проверка готовности GPU:

```bash
nvidia-smi                                   # драйвер и видеокарты видны
python -c "import torch; print(torch.cuda.is_available(), torch.cuda.device_count())"
```

Если ни один воркер не запущен, сервер штатно продолжает работать: задачи остаются в статусе `queued`, отчёты ходов публикуются без иллюстраций (см. п. 5.2, шаг 5).

## 5. Порядок запуска

### 5.1. Запуск сервера мира в процессе (библиотечный режим)

Ядро поднимается одной композицией `WorldServer` (§15). Пример полностью рабочего запуска (проверено):

```python
from datetime import datetime, timezone
from poem.api import WorldServer
from poem.chronology import Civilization
```

### 5.2. Продактив-запуск (HTTP + PostgreSQL)

Типовая обвязка (FastAPI-подобный пример; handlers не меняются):

```python
# wsgi/asgi entrypoint — пример минимальной привязки маршрутов /api/v1/* к server.handle
from poem.api import WorldServer
server = WorldServer(world_id=os.environ["POEM_WORLD_ID"])

@app.post("/api/v1/laws/drafts")
async def create_draft(body: dict):
    return server.handle("POST", "/api/v1/laws/drafts", body)
```

Порядок боевого запуска:

1. поднять PostgreSQL, применить `schema.sql` (п. 4.3);
2. положить `config/chronology.toml` рядом с процессом (переменная пути — на усмотрение обвязки);
3. запустить HTTP-обвязку (`uvicorn app:app --host 0.0.0.0 --port 8000` для FastAPI);
4. настроить планировщик хода (§6.1 design): ежедневно открывать ход, выставлять `simulation_cutoff_at` (например, 20:00 серверного времени) и вызывать `turns/run`; публикация отчёта — шаг 22 пайплайна выполняется внутри `run_turn`;
5. запустить воркер(ы) генерации изображений **на локальных видеокартах сервера** (установка — п. 4.5): поллинг `GET /api/v1/worlds/{id}/images`, `POST /api/v1/images/{task_id}/claim`, локальный инференс (GPU, без обращений к сторонним сервисам), затем `.../complete` с байтами в `asset_base64` (сервер сохранит файл в своём `asset_dir`) либо только с `asset_ref` при расшаренном томе; при ошибке — `success:false` и текст в `error`. Клиентская раздача готовых картинок идёт с самого сервера через `GET /api/v1/images/{task_id}/asset`. Сколько GPU на сервере — столько процессов-воркеров можно держать; без воркеров игра работает, иллюстрации просто копятся в очереди;
6. включить резервное копирование БД (ревизии законов — юридически значимое состояние игры).

### 5.3. Остановка и обслуживание

- штатная остановка — SIGTERM HTTP-процесса; незавершённый ход при этом остаётся в статусе `Simulating`/`Finalizing` и должен быть перезапущен планировщиком (ход идемпотентно переоткрывается по `seed`);
- правки, присланные после `simulation_cutoff`, не теряются: они имеют статус `Pending` и войдут в следующий срез;
- диагностика состояния мира: `GET /api/v1/worlds/{id}/chronology`, `GET /api/v1/laws/pending`, `GET /api/v1/laws/snapshot`.

## 6. Справочник API сервера (§15)

Все запросы — JSON. Префикс `/api/v1`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/laws/drafts` | создать серверный черновик (`civilization_id`, `raw_text`, опц. `target_law_id`) |
| PUT | `/laws/drafts/{id}` | обновить черновик (текст/каноническую форму) |
| GET | `/laws/drafts` | список черновиков (`civilization_id`) |
| GET | `/laws/drafts/{id}` | получить черновик (доступен с любого устройства) |
| DELETE | `/laws/drafts/{id}` | удалить черновик |
| POST | `/laws/drafts/{id}/validate` | вердикт нейросетевого слоя над текстом черновика (§3.3, TASK-066): формализация в каноническую норму, проверка противоречивости и конкретности; при успехе статус `Validated`, при провале — `Invalid`, черновик остаётся на сервере редактируемым; вердикт не зависит от времени суток |
| POST | `/laws` | создать закон (`title`, `raw_text`, `canonical{kind,scope,effect}`) |
| GET | `/laws` | список законов (фильтр `civilization_id`) |
| GET | `/laws/{id}` | карточка закона: версия, черновики, ожидающие правки, история, переходы, традиция, конфликты, фольклор (§16.2) |
| GET | `/laws/{id}/status` | статус правок закона (в каком ходу будет учтена; без штрафов за время подачи) |
| POST | `/laws/{id}/revisions` | записать ревизию (`action`: CreateDraft/UpdateDraft/SubmitDraft/AmendLaw/RepealLaw/SuspendLaw/ReinstateLaw/ClarifyLaw/CancelPendingChange) |
| POST | `/laws/{id}/cost_preview` | предпросмотр стоимости правки (административный ресурс) |
| POST | `/laws/{id}/revisions/{rid}/submit` | подтвердить ревизию / преобразовать черновик (`draft_id`) / отклонить (`reject_reason`) |
| POST | `/laws/{id}/revisions/{rid}/cancel` | отменить неподтверждённую правку |
| GET | `/laws/{id}/revisions` | история ревизий закона |
| GET | `/laws/pending` | какие правки войдут в следующий срез, вошли в текущий, перезаписаны, отклонены |
| GET | `/laws/snapshot` | снимок активных законов, который читает симуляция (§4.3) |
| GET | `/worlds/{id}/chronology` | текущий ход/год/сезон/эпоха + прогноз интервала следующего хода (эпоха пересчитывается по зарегистрированным цивилизациям, §9) |
| POST | `/worlds/{id}/civilizations` | зарегистрировать цивилизацию (`id`, `name`, `progress`; опц. `active`, `population`, `annual_production_rate`, `annual_growth_rate`, `annual_research_rate`, `culture_modifier`, `technology_modifier`, `administrative_budget`, `research_to_progress`). Повторный `id` → 400. Цивилизации определяют эпоху мира и интервал хода |
| POST | `/worlds/{id}/turns/open` | открыть ход (`started_at`, `simulation_cutoff_at`, `seed`) |
| POST | `/worlds/{id}/turns/run` | просимулировать и опубликовать отчёт (допускается one-call: можно передать `started_at`+`simulation_cutoff_at` сразу) |
| GET | `/worlds/{id}/turns/report` | последний опубликованный отчёт хода |
| POST | `/treaties` | заключить договор (длительность в **игровых** годах) |
| POST | `/wars` | объявить войну (усталость считается в игровом времени) |
| GET | `/worlds/{id}/images` | очередь задач генерации иллюстраций (статусы queued/running/done/failed, `claimed_by`, `asset_ref`) |
| POST | `/images/{id}/claim` | забрать задачу локальному GPU-воркеру (`worker_id`, `lease_seconds`; истёкшая аренда воркера автоматически возвращает задачу в queued) |
| POST | `/images/{id}/heartbeat` | продлить аренду задачи при длительном рендере |
| POST | `/images/{id}/complete` | завершить задачу (`success`; байты — в `asset_base64`, путь — в `asset_ref`; при ошибке — `error`) |
| GET | `/images/{id}/asset` | получить готовую иллюстрацию с собственного хранилища сервера (base64, media_type, sha256) |
| GET | `/worlds/{id}/images/metrics` | метрики очереди рендеринга для админ-панели: глубина по статусам, загрузка GPU-воркеров (`by_worker`), возвраты осиротевших аренд, среднее время ожидания/рендера, доля успеха |

Ответы содержат человекочитаемые уведомления (§16.3), например:

```text
Правка сохранена на сервере.
Она будет учтена при симуляции хода.
Время подачи не влияет на эффективность.
```

## 7. Журнал операций (чек-лист администратора)

1. **Старт мира**: создать `WorldServer`, добавить цивилизации, применить `chronology.toml`.
2. **Ежедневный цикл**: `turns/open` (утром) → приём правок → `turns/run` после `simulation_cutoff` → публикация отчёта.
3. **Мониторинг**: ошибки валидации возвращаются как `status: 400` с текстом причины; сбои применения ревизий помечаются статусом `Failed` и видны в `GET /laws/pending`.
4. **Обновление правил баланса**: только через `config/chronology.toml` (интервалы/скорости) — без правок кода.
5. **Тесты перед релизом**: `python -m pytest -q` — все 172 теста должны проходить; они фиксируют ключевые инварианты (время суток не влияет, последняя подтверждённая версия побеждает, правки после среза переносятся, интервалы динамические, договоры истекают по игровому времени, LLM-тексты воспроизводимы и деградируют в шаблон при сбое провайдера).
